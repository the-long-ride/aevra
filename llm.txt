## 1. What is Aevra?

Aevra is a workspace-scoped local MCP (Model Context Protocol) execution gateway that connects AI web clients and assistants (ChatGPT, Claude, Grok, Gemini, Manus, Cursor, Langdock, etc.) directly to your machine. It enables AI assistants to inspect directories, read and write files, execute shell commands, manage Git repositories, launch background processes, control Chromium browsers, and automate native applications through Windows UIA, macOS Accessibility, and Linux AT-SPI under explicit, human-controlled security boundaries.

### Central Invariant

> **The Core decides authority. The Worker executes only the exact authority it receives.**

The gateway is architected as an out-of-process system where untrusted AI instructions never have direct operating system access. Instead, every request is verified against active capability profiles, explicit workspace grants, and policy rules before any instruction reaches the execution worker.

```text
                             │
   ┌─────────────────────────┴─────────────────────────┐
   │                                                   │
MCP Data Plane (Port 47832)               Admin Control Plane (Port 47831)
Aevra Core Daemon                         React 19 Admin Web UI
- Session & Lease Manager                 - Interactive Approvals
- Policy Engine & Capability Profiles     - Workspaces & Mount Points
- Floating-IP OAuth Continuity            - Live MCP Activity Timeline
- Token Bucket Rate Limiting              - Token Usage Stats & History Chart
- Token Metering & MCP Result Shaper      - Connector Tool Surfaces & Settings
   │
   ▼ (Local Authenticated IPC - Named Pipe / Unix Domain Socket)
Execution Worker (Port 47833 WebSocket for Browser Extension)
   ├─ Filesystem Sandbox (Scoped to permitted workspace roots & mounts)
   ├─ Shell Execution & Detached Background Processes
   ├─ Desktop Automation (Windows UIA · macOS AX · Linux AT-SPI semantic control)
   ├─ Browser Control (Chromium MV3 Extension & CDP)
   └─ Upstream MCP Proxies & Docker / Podman Sandbox
```

### Port Allocation & Custom Listeners

- **Default Ports**:
  - **Port 47830 (`AEVRA_PUBLIC_PORT`)**: Public gateway entry point for inbound web clients.
  - **Port 47831 (`AEVRA_ADMIN_PORT`)**: Local Admin Web UI and HTTP administrative API.
  - **Port 47832 (`AEVRA_MCP_PORT`)**: MCP HTTP / SSE transport protocol.
  - **Port 47833 (`AEVRA_BROWSER_PORT`)**: WebSocket listener for the paired Chromium browser extension.
- **Custom Ports**:
  - Shift all listeners using `--basePort=<port>` (e.g. `--basePort=50000` moves the block to `50000`–`50003`).
  - Or override individual listeners: `--gateway-port` (`--gp`), `--ui-port` (`--up`), `--mcp-port` (`--mp`), and `--ws-port` (`--wp`).
  - User service commands (`aevra service install|start|restart`) accept and persist these port configurations.
- **Streaming IPC**:
  - The Core daemon and Execution Worker communicate via local authenticated IPC (named pipes / Unix domain sockets) with streaming binary framing (`packages/ipc/src/stream.ts`) for high-throughput file transfers and safe discard/recovery on worker restarts.

## 3. Security Model & Policy Boundaries

1. **Capability Profiles**:
   - `Minimal`: Safe introspection only (`aevra_status`).
   - `Read-Only`: Non-mutating directory listing, file reading, and searching.
   - `Safe Dev`: Standard dev commands matching safe regex patterns (e.g. `npm test`, `git status`, `cargo check`) run without prompting; modifying critical paths requires approval.
   - `Power Dev`: Full workspace file editing, command execution, and managed processes with step-up approvals for sensitive actions.
   - `Full Access`: Complete execution access for local development.

2. **Approval Scopes (Human-in-the-Loop)**:
   - `once`: Approve a single execution of the exact command or tool call.
   - `session`: Permit this tool/command for the duration of the AI connection session.
   - `workspace`: Persist permission for this workspace across sessions.
   - `global`: Persist permission across all workspaces on this machine.

3. **Data Protection & DLP (Data Loss Prevention)**:
   - `SECRET` Paths: Critical system paths (`~/.ssh`, `id_rsa`, `.env`, credentials) are strictly denied.
   - `SENSITIVE` Paths: Token-bearing or internal configuration paths trigger step-up approval.
   - DLP Redaction: Output streams automatically redact API keys, JWTs, bearer tokens, private keys, and high-entropy secrets before sending responses back to the LLM.
   - Symlink Traversal Protection: Realpath canonicalization blocks directory traversal attacks using relative `..` segments, symlinks, or hard-link aliases.

4. **Floating-IP OAuth Continuity**:
   - Cloud AI runners (such as OpenAI ChatGPT or Anthropic Claude) rotate outbound egress IP addresses on every prompt.
   - Aevra decouples identity from IP addresses using cryptographic session subjects and rotating refresh tokens, preserving workspace leases across runner IP shifts.
   - Uses atomic execution claims (`claimExecution`) to guarantee that parallel cloud runners never double-execute the same approved operation.

5. **Host Control Grants & Per-Connector Tool Surfaces**:
   - `browser.control` and `desktop.control` require explicit host connection grants, decoupled from workspace selection.
   - Operators can scope tools per client connection into tool groups: `core` (always on), `files`, `commands`, `git`, `changes`, `skills`, `browser`, `desktop`, `control`, and `upstream`.
   - Invoking a tool in a disabled group returns error code `TOOL_GROUP_DISABLED`.

6. **YOLO Policy Settings (`policy.yolo` = `{mode, risk}`)**:
   - Evaluated only when a connection has YOLO enabled.
   - **Risk (`risk`)**:
     - `prevent-high-risk` (default): CRITICAL actions, `policy.critical.alwaysConfirm`, and file transfers still ask for human approval.
     - `do-whatever`: Waives confirmation for CRITICAL commands, permanent file deletion, and `git push` only when scope is `unrestricted`. Non-command tools (e.g. `files_download`, `files_upload`) skip approvals under `do-whatever` in either scope.
   - **Scope (`mode`)**:
     - `workspace` (default): Unattended execution is strictly constrained inside workspace roots. Commands outside or of unknown scope, host execution, and network access still prompt.
     - `unrestricted`: Lifts scope boundaries, allowing directory actions outside registered workspaces.
   - Conclusively workspace-scoped commands run unattended under any YOLO setting before rule checks. Secret paths and DLP rules strictly apply in all configurations.

7. **Multi-Workspace Grants & Admission Profiles**:
   - Connectors can be granted access to multiple workspaces simultaneously upon creation or update (or none by default).
   - Each grant defines:
     - **Admission Profile**: `full`, `read-only`, or `custom`.
     - **Admission Mode**: `standard` or `isolated`.
     - **External Mounts**: `read-only`, `read-write`, or `blocked`.
   - Local and public tunnel configurations are generated side-by-side. Tool calls against multi-workspace sessions must provide the `workspace` parameter explicitly.

## 4. Built-in MCP Tools Reference (79 Tools)

The model-facing surface favors bounded batch interfaces; singular file/command
primitives remain internal implementation details.

### Status, Workspace & Connector Notes

- Status: `aevra_status` (reports session, leases, capabilities, and system info), `control_access_status` (reports connection-level host browser/desktop grants).
- Workspace: `workspace_list`, `workspace_select`, `workspace_current`.
- Connector Notes:
  - `notes_list`: List notes left by the human operator for the current connector (`id`, `title`, `preview`, `imageCount`, `aiCanDelete`, `readOnConnect`, `updatedAt`).
  - `notes_read`: Read a note by `id` (returns text, metadata, and attached images up to 4 images / 2 MiB each as MCP image content).
  - `notes_delete`: Permanently delete a note by `id` (only permitted when `aiCanDelete` is true).

### Files, Commands, Git, Processes

- Files/search: `file_list`, `file_read_many`, `file_search`, `search`,
  `file_write_many`, `file_move`, `file_delete`. File contents are preserved verbatim.
- Binary transfer: `files_download` (send 1-64 files to device: inline base64 or public `url`; streams to temp file, verifies pinned public DNS, reports `mimeMismatch`, `overwrite` defaults to false, snapshots files ≤ 20 MiB for recovery) and `files_upload` (pull 1-64 files from device: `delivery: "auto" | "inline" | "link"`; `auto` stays inline up to 4 MB then switches to links; `link` mints 5-minute single-use download links `GET /files/<secret>` on public origin). One `files:transfer` approval per batch (waived under YOLO risk `do-whatever`).
- File transfer error codes: `FILE_EXISTS`, `FILE_CHANGED`, `URL_NOT_PUBLIC`, `URL_SCHEME`, `TOO_MANY_REDIRECTS`, `SIZE_LIMIT`, `URL_TIMEOUT`, `INLINE_TOO_LARGE`, `BATCH_LIMIT`, `PUBLIC_URL_REQUIRED`.
- Commands: `command_run_many` and `shell_run`. Supports optional `maxOutputChars` budget (256–200,000, default 16,000). Use managed processes for long-running work.
- Processes: `process_start/list/status/wait/logs/stop/restart`.
- Git: `git_status/add/diff/log/branch/commit/push`.
- Durable mutation inspection: `operation_get`, `operation_list`.
- Change sets: `change_begin/status/commit/rollback`.
- Approvals: `approval_status/wait/cancel`. Supports optional `detail: "summary" | "full"` (default `"summary"` to prevent token waste during polling).
- Skills/instructions: `skills_list`, `skill_read/write`, `instructions_read/write`.

### Browser Automation (Chromium MV3 Extension & CDP)

Ten `browser_*` tools provide lifecycle (`browser_connect/status/disconnect`), tabs/navigation (`browser_tabs/navigate`), accessibility or vision snapshots (`browser_snapshot`), page reads (`browser_read`), ordered actions (`browser_act_many` with coordinate `click` and `drag`), a bounded Playwright-like `browser_execute_script` fast lane, and logs (`browser_logs`). Operates as a true background auto-clicker without stealing window focus. Credential-shaped field values are omitted and model typing into credential fields is refused.

### Guarded Control Plans

- `control_observe`: bounded semantic browser/desktop observation.
- `control_execute`: strict schema-version-1 finite plan with dependencies,
  guards, postconditions, bounded output, and independent-surface concurrency.
- `control_plan_status` / `control_plan_cancel`: owner-bound durable lifecycle.
- `desktop_act_many`: semantic desktop batch convenience API.

Matching request IDs use a durable keyed digest. Incomplete plans become unknown
after restart and are not replayed. Strict `isolated` mode is fail-closed
until a separately provisioned runner has verified containment.

### Desktop Automation

Shared semantic control is available through Windows UIA, macOS Accessibility
(AX), and Linux AT-SPI2. Prefer `desktop_describe(mode:"background")` plus
`desktop_invoke`, `desktop_set_value`, `desktop_select`, or
`desktop_toggle`; these provider actions do not synthesize host mouse/keyboard
input. Explicit foreground click/type/key/scroll and pixel capture adapters cover Windows, macOS 13+, Ubuntu X11, GNOME Wayland and KDE KWin 6.6. macOS needs Accessibility plus Screen Recording, and native acceptance is pending. X11 needs XTest and a compositing window manager. Linux capture/input covers X11 and GNOME Wayland through an explicitly installed/enabled companion with approved helper path; see docs/user-manual/22-wayland-desktop.md. GNOME 50 native acceptance passes; GNOME 46 is a required CI target. KDE KWin 6.6 now has a native plugin; software-rendered native acceptance passes, while GPU capture acceptance remains pending. No XWayland or uinput fallback is used. Capability flags report actual probed readiness. `desktop_request_access` submits a
pending request for human review when an attributed application is refused.
When `AEVRA_DESKTOP_HELPER_PATH` points to a missing file, Aevra safely falls back
to bundled or Cargo helper binaries.

Both hosts consume one canonical native helper library with a shared guarded input executor. Authorized window reads retain their original process/window identity and are rechecked before publishing; standalone also rechecks its current allowlist. Disconnect/reconnect invalidates connection generations and old refs/mappings; cancelled connects and stale in-flight reads cannot restore authority. Observe again after recovery.

### Upstream MCP Proxies

External MCP servers (stdio, SSE, HTTP) can be registered via Admin UI or
`aevra mcp add`. Their tools are projected under namespaced tool names (`server__tool`)
and remain subject to Aevra policy/audit boundaries. A server can be disabled
(`aevra mcp disable <id>`, Admin UI switch, `POST /api/mcp/upstreams/{id}/disable`):
it is hidden from lists, its worker session is closed, and calls/test/refresh fail with
`MCP_UPSTREAM_DISABLED` until re-enabled. Changes are audited as `mcp.upstream.enable`/`disable`
and are seen by connected clients on their next list (no `list_changed` is sent). If an upstream changes its catalog it is held in `needs-review` and its tools are not served until an admin accepts the change: the Admin UI list shows a warning icon in the leftmost column that opens a review dialog with **Accept changes**, `aevra mcp list` marks the server with `!` and prints a hint, and `aevra mcp review <id>` / `aevra mcp accept <id> --yes` show and accept the diff. The list checks for pending changes on every load, and accepting is audited as `mcp.upstream.acknowledge`.

### Local AI Agent Integration

`aevra agent` connects local coding agents (`codex`, `claude-code` with alias `claude`, `opencode`, `antigravity`, `antigravity-cli` with alias `agy`, `antigravity-ide`) to a running Aevra. `aevra agent list` (alias `status`) shows each agent, whether it was detected (command name on `PATH` or a config home; no process is spawned), its scope (`global` or a workspace name), transport, state and last use. `aevra agent install` with no agent names acts on the detected agents after a `Proceed? [y/N]` question (`--yes` skips it; without a terminal and without `--yes` it prints the list and exits 1; `all` with nothing detected exits 1; `--dry-run` never prompts). Naming an agent installs it even if it was not detected. Several agents run independently and the exit code is 1 if any fails. `--json` prints one JSON document on stdout and never prints credential file paths or hashes.

- Scope: `--scope user|workspace` (default `user`). `--workspace <name|id>` implies workspace scope and is resolved through the registered Aevra workspaces. `uninstall <agent>` without `--scope` removes the global connection; with `--workspace` and no `--scope` it removes that workspace connection; `uninstall all` without `--scope` removes every connection, global and workspace (API: `scope: 'all'`); with `--scope user` it removes global connections only and never touches workspace ones; each agent is removed independently, so one failing agent does not stop the others (exit code 1). `aevra agent uninstall --id <id>` (API: `credentialId`, uninstall only, not combinable with agent names, `all`, `--scope` or `--workspace`) removes exactly one connection by its connection id, also when its workspace folder was deleted or is no longer a registered Aevra workspace (the registration is removed and its credential revoked; a note says the entry file could not be edited); `agent list` prints the id of such orphaned connections, and Settings removes them with Remove (Update stays disabled).
- Workspace scope is stdio only (`--transport http` is refused), installs no skill and creates no skill links. The entry goes to:
  - Codex: `<root>/.codex/config.toml` (Codex reads it for trusted projects only)
  - Claude Code: `~/.claude.json` (or `$CLAUDE_CONFIG_DIR/.claude.json`) under `projects[<root>]` (local scope, nothing written into the project folder)
  - OpenCode: `<root>/opencode.json` or an existing `opencode.jsonc`
  - Antigravity / Antigravity CLI / Antigravity IDE: `<root>/.agents/mcp_config.json`
- User scope entry targets:
  - Codex: `~/.codex/config.toml`
  - Claude Code: `~/.claude.json`
  - OpenCode: `~/.config/opencode/opencode.json`
  - Antigravity: `~/.gemini/antigravity/mcp_config.json`
  - Antigravity CLI: `~/.gemini/antigravity-cli/mcp_config.json`
  - Antigravity IDE: `~/.gemini/config/mcp_config.json`
- A project file tracked by git is refused with `AGENT_PROJECT_FILE_TRACKED`; otherwise it is added to the repository `info/exclude`. A symbolic link or directory junction on the way to the file inside the project is refused with `AGENT_PATH_CONFLICT`; a workspace folder that is the home folder or a filesystem root, or a project file that is the agent's own global file, is refused with `AGENT_OPTIONS_INVALID` (dry runs included). git runs only from an absolute `PATH` entry outside the project (device paths and 8.3 short names of the project are recognised); when the folder or a parent holds `.git` but no such git exists, the install goes ahead with the note `git could not be found outside the project folder <root>, so git tracking was not checked.` The link refusal also applies to uninstall and status: remove the link, uninstall again, then delete the leftover `aevra` entry by hand in the file the link pointed to. After install: trust the folder in Codex; start Claude Code in the folder and restart it.
- The stdio bridge that generated configs start is `aevra agent serve --credential-file <file>`. It replaces `aevra mcp serve --stdio` with no alias: configs written by earlier local builds are refreshed by running `aevra agent install <agent>` again with the same scope (or Update in Settings): a changed stdio entry is rewritten in place and keeps its credential; after an MCP port or TLS CA change the stdio credential file gets the current endpoint and CA file (same id and token) and an HTTP entry is rewritten with the stored credential (never a new one); an identical connection is `no change`.
- Uninstall acts only on registrations Aevra recorded: a hand-written `aevra` entry is left alone and does not block it; a managed entry, credential file or skill modified since install refuses the uninstall (nothing is removed) and root `aevra uninstall` then skips cleanup and `--purge`.
- The Admin UI Settings page shows the connections table (with Last used) and a Connect dialog: detected agents, global or several workspaces (stdio only), dry-run preview and per-agent results.
- Uninstall saves config edits and the connection record first and revokes credentials last; a failed revoke fails the command with `AGENT_REVOKE_INCOMPLETE` (naming the credential ids) and leaves the saved files. Git exclude and file cleanup failures after the save are notes only. Settings Remove asks for confirmation; a connection with a deleted credential shows `Credential missing` (CLI `missing`, state `incomplete`).

### Token Efficiency, Result Shaping & Transport (v1.2.0)

- **Advertised Schema Compaction:** `tools/list` omits deprecated properties, default-false hints (`readOnlyHint`, `idempotentHint`), and bare output schemas, keeping definition size under 56,000 characters (~20% token savings).
- **Result Shaper:** Compacts tool results automatically at the MCP edge:
  - Unwraps `{ ok: true, value: X }` -> `X` on command/shell results.
  - Flattens batch arrays (`file_read_many`, `file_write_many`, `command_run_many`), dropping duplicate `path`, array `index`, and default `sensitivity: NORMAL`, while hoisting `untrusted` notices once to top level. Drops `failed: 0` and `skipped: 0` from summaries.
  - Drops `signal: null` and empty `stderr: ""` from command results.
  - Strips whole ANSI CSI/OSC escape sequences at the source, normalizes CRLF, collapses 3+ repeated lines, and enforces `maxOutputChars` budgets (head 25% + tail 75% with `truncated: true`).
  - Approval tickets return concise summaries by default unless `detail: "full"`.
  - File content (`file_read*` `content`) is strictly unaltered byte-for-byte.
- **Per-Connector Result Formats:** Configurable in Admin UI as `both` (dual text + structured, default), `text` (text only), or `structured` (`structuredContent` only).
- **Token Estimation & Analytics:** Estimates text tokens using `heuristic-v1` (ASCII `ceil(len/4)`, CJK/emoji 1.0, others 0.5). Accumulated in memory and flushed to SQLite (`token_usage` table) every 30s. Displayed in live stat boxes and SVG historical charts on the Admin Dashboard.
- **HTTP Response Compression:** Gzip-compresses responses ≥ 1,024 bytes when the client sends `Accept-Encoding: gzip`.
- **Bounded Activity Detail:** Sanitized in-memory activity logs are bounded to prevent memory bloating.

### File Transfer, Tool Switches, Notes & YOLO Split (v1.3.2)

- **File Transfer Tools:** `files_download` (pull files to workspace via inline base64 or verified public URLs with pinned DNS and MIME sniffing) and `files_upload` (push files out of workspace inline or via short-lived 5-minute single-use download links `GET /files/<secret>`). Configurable limits via Settings > File Transfer (`files.transfer`, default 200 MB file, 500 MB batch, 50 MB inline).
- **Global Per-Tool Switches:** Operators can globally turn off individual built-in or linked upstream MCP tools in Settings > Tools (`tools.disabled`), removing them from `tools/list` and rejecting invocations by name with `TOOL_DISABLED`. Core primitives (`workspace_*`, `operation_*`, `approval_*`, `aevra_status`, `control_access_status`) remain locked on (`TOOL_LOCKED`).
- **YOLO Policy Split:** Split into independent Scope (`workspace|unrestricted`) and Risk (`prevent-high-risk|do-whatever`) settings (`policy.yolo`). Unrestricted scope lifts workspace boundary checks; `do-whatever` risk waives approvals for CRITICAL operations only when unrestricted scope is enabled. Non-command tools (such as file transfers) skip approvals under `do-whatever` in either scope.
- **Connector Multi-Workspace Grants:** Connectors can be granted access to multiple workspaces upon creation or update (or none by default), with per-workspace admission profiles, admission modes, and external mount capability ceilings. Dual Local & Tunnel configuration snippets are generated side-by-side.
- **Connector Notes:** Operators can leave persistent guidance, instructions, and up to 4 images per note for AI clients via the Notes tab in connection details. Tools: `notes_list`, `notes_read` (serves images as MCP image content), and `notes_delete` (only when `aiCanDelete` is enabled).

## 6. How to Connect AI Clients

### Connecting ChatGPT (OpenAI)

1. In Aevra Admin UI, go to **Dashboard** or **Settings** -> **Remote Access** and ensure a public tunnel (Cloudflare, ngrok, or Direct HTTPS) is active.
2. In ChatGPT, create a Custom GPT or action.
3. Set Authentication to **OAuth**:
   - Authorization URL: `<Your-Public-Gateway-URL>/oauth/authorize`
   - Token URL: `<Your-Public-Gateway-URL>/oauth/token`
4. Provide the MCP Server URL: `<Your-Public-Gateway-URL>/mcp`.
5. Authenticate via the browser prompt and grant permission to one or more workspaces.

### Connecting Claude (Anthropic)

1. Add an MCP server definition in Claude Desktop or Claude Web connector settings.
2. URL: `<Your-Public-Gateway-URL>/mcp`.
3. Complete OAuth PKCE handshake in the browser.

## 7. Crucial Tips for AI LLMs Assisting Users

When you are acting as an AI assistant interacting with Aevra via MCP tools or guiding a human operator:

### Tip 1: Always Target Workspaces Explicitly

- When a user grants access to **multiple workspaces** in one connection session, `SessionManager.activeLease(sessionId)` intentionally returns `null` because no single workspace is unambiguous.
- **Rule**: In workspace-scoped tool calls (`file_read_many`, `file_write_many`, `command_run_many`, `search`, etc.), ALWAYS specify the `workspace` parameter explicitly:
  ```json
  {
    "workspace": "my-project",
    "path": "src/index.ts"
  }
  ```
- Omitting `workspace` in multi-workspace sessions causes `SESSION_WORKSPACE_REQUIRED: Select a workspace first`.

### Tip 2: Batch File Operations to Save Roundtrips

- Use `file_read_many` instead of repeated singular reads:
  ```json
  {
    "workspace": "my-project",
    "paths": ["package.json", "tsconfig.json", "src/index.ts"]
  }
  ```
- Instead of writing files one by one, use `file_write_many` for multi-file edits.

### Tip 2b: Moving binary files

- Send a file you made: `files_download` with `content` + `encoding: "base64"` and a `mimeType`. Send a big or existing file: use a public `url` (private and local addresses are refused after DNS resolution across redirects).
- Fetch a device file: `files_upload`. Delivery modes:
  - `delivery: "auto"` (default): stays inline base64 up to 4 MB total, then switches to links.
  - `delivery: "inline"`: forces inline base64 up to the configured inline limit (default 50 MB). If links fail with `PUBLIC_URL_REQUIRED`, fall back to `inline`.
  - `delivery: "link"`: always mints a one-time link `GET /files/<secret>` on your public MCP origin. Fetch it once within 5 minutes; it dies after 1 successful download or when your connection is revoked/disconnected.
- File transfer errors to handle: `FILE_EXISTS`, `FILE_CHANGED`, `URL_NOT_PUBLIC`, `URL_SCHEME`, `TOO_MANY_REDIRECTS`, `SIZE_LIMIT`, `URL_TIMEOUT`, `INLINE_TOO_LARGE`, `BATCH_LIMIT`, `PUBLIC_URL_REQUIRED`.
- Tools switched off in Settings > Tools are omitted from `tools/list` and refused by name with `TOOL_DISABLED`. Core tools remain permanently locked on (`TOOL_LOCKED`).

### Tip 3: Use managed processes for long-running commands

- Commands like `npm run dev`, `python -m http.server`, `vite`, `cargo watch`, or interactive prompts (`git log` without paging disabled) will block until the command timeout expires (default 60s) and fail!
- **Rule**: For persistent servers or background watchers, always use:
  1. `process_start(workspace, "npm", ["run", "dev"])` -> returns `processId`.
  2. `process_logs(processId)` -> inspect stdout/stderr to verify startup.
  3. `process_stop(processId)` -> terminate when work is finished.

### Tip 4: Respect DLP and Security Boundaries

- Never attempt to read files like `~/.ssh/id_rsa`, `.env.production`, or OS system directories. Aevra will block the request and log a policy violation.
- If a command requires human approval, politely inform the user that an approval prompt is waiting in their Aevra Admin UI.

### Tip 5: Safe Command Execution

- Read-only commands such as `git status`, `git diff`, `npm test`, `cargo check`, `pytest` match safe command matchers and run instantly under the Safe Dev profile without interrupting the user.
- Prefer non-interactive flags (e.g. `--yes`, `-y`, `--no-pager`, `CI=true`) to ensure commands do not wait for stdin.

### Tip 6: Handling Browser & Desktop Actions

- For browser actions, verify that the browser extension/CDP transport is connected (reportable via `aevra status` or `aevra_status`).
- Prefer shared semantic desktop actions on every supported OS. Use Windows foreground input only when explicitly required; never treat it as fallback for `sharedSemantic` or `isolated` plans.

### Tip 7: Managing Command Output Budgets (`maxOutputChars`)

- `shell_run`, `command_run`, and `command_run_many` enforce an output budget per stream (default 16,000 characters). When output exceeds the budget, Aevra retains the first 25% and last 75%, joined with `… [N chars omitted] …`, and sets `truncated: true`.
- If you expect very large output or want to strictly constrain output to save context tokens, pass `maxOutputChars` (256 to 200,000) explicitly:
  ```json
  {
    "workspace": "my-project",
    "commands": [{ "command": "npm", "args": ["test"] }],
    "maxOutputChars": 32000
  }
  ```

### Tip 8: Lightweight Approval Polling (`detail: "summary"`)

- Polling pending approvals via `approval_status` or `approval_wait` returns a concise summary by default (action, summary, risk, expiration), saving thousands of tokens per poll.
- Avoid passing `"detail": "full"` on recurring polling loops. Only request `"detail": "full"` when you specifically need the complete command analysis graph or full raw script text.

### Tip 9: Handling Scoped Tool Surfaces (`TOOL_GROUP_DISABLED`)

- If a tool invocation returns `TOOL_GROUP_DISABLED: Tool <name> is in the "<group>" group, which is disabled for this connector`, the administrator has filtered your tool surface in **Connections > Tool surface** to conserve context tokens.
- Available groups: `core` (always on), `files`, `commands`, `git`, `changes`, `skills`, `browser`, `desktop`, `control`, `upstream`.
- If your task strictly requires tools from a disabled group, inform the operator so they can toggle the group on in the Aevra Web UI.

### Tip 10: Utilizing Connector Notes (`notes_list`, `notes_read`, `notes_delete`)

- Human operators can attach notes and visual reference assets directly to your connector in the Web UI:
  - Call `notes_list` to discover available notes for your connection.
  - Call `notes_read` with `{ "id": "<note-id>" }` to retrieve full note markdown and attached images (PNG/JPEG/GIF/WebP, up to 4 images / 2 MiB each returned as native MCP image content blocks).
  - Only call `notes_delete` if the user explicitly enabled `aiCanDelete: true` on that note and asked you to clean it up.
- Visible notes with **Read on connect** enabled are automatically flagged during session establishment for immediate ingestion.

### Tip 11: Adapting to YOLO Policy Risk & Scope

- When operating with YOLO mode enabled:
  - Commands conclusively within the workspace run unattended under any YOLO configuration.
  - Commands outside the workspace or of unknown scope require human approval unless scope is set to `unrestricted`.
  - Under risk `prevent-high-risk` (default), CRITICAL operations and file transfers still prompt for human approval. Under risk `do-whatever`, CRITICAL operations run unattended (when scope is `unrestricted`), and non-command tools (such as file transfers) skip approvals under either scope.
  - Secret paths and DLP redaction remain enforced in all YOLO modes without exception.
